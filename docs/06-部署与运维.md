# 06-部署与运维

> 状态：M4-wave2 实测版（2026-09-04 旁路部署落机，切换 runbook 见第七节）。
> 旧网关在本文档中一律中性称呼为「旧网关（legacy）」。

## 一、目标部署形态

- 单台 Linux 服务器（Ubuntu），systemd 托管单进程；
- SQLite 数据文件 + 定期备份；
- 生产监听 3000，旁路验证用 3100。

## 二、交叉编译

Windows 开发机（PowerShell）：

```powershell
$env:CGO_ENABLED='0'; $env:GOOS='linux'; $env:GOARCH='amd64'
go build -trimpath -ldflags "-s -w -X main.version=<tag> -X main.commit=<sha>" -o bin/hui-api-linux-amd64 ./cmd/hui-api
go build -trimpath -ldflags "-s -w" -o bin/migrate-linux-amd64 ./cmd/migrate
```

> 纯 Go SQLite 驱动 + `CGO_ENABLED=0`，任何平台可直接交叉编译出 Linux 二进制。
> 本地与服务器双侧 MD5 校验（`Get-FileHash -Algorithm MD5` vs `md5sum`）后再用。

Linux 侧上传后：

```bash
chmod 755 hui-api-linux-amd64 && ./hui-api-linux-amd64 -version
```

## 三、systemd 单元（M4-wave2 生产实测版）

`/etc/systemd/system/hui-api.service`（旁路态，config 键位对齐 config.example.yaml）：

```ini
[Unit]
Description=hui-api LLM gateway (bypass 127.0.0.1:3100)
After=network.target

[Service]
Type=simple
User=ubuntu
WorkingDirectory=/home/ubuntu/hui-api
ExecStart=/home/ubuntu/hui-api/bin/hui-api-linux-amd64 -config /home/ubuntu/hui-api/config/config.yaml
Environment=GOMEMLIMIT=120MiB
Restart=on-failure
RestartSec=3
MemoryMax=400M
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
```

config（`/home/ubuntu/hui-api/config/config.yaml`，chmod 600；键位对齐 config.example.yaml）：

```yaml
addr: "127.0.0.1:3100"                          # 切换接管时改 ":3000"（见第七节）
sqlite_path: "/home/ubuntu/hui-api/data/hui-api.db"
session_secret: "<openssl rand -hex 32，服务器端生成一次固化，不落仓库>"
```

## 四、备份策略

1. **迁移前自动备份**：进程启动执行 schema 迁移前，先对 db 文件做快照备份（`.db.gz`）；
2. **日常定时备份**：cron 每日 `sqlite3 .backup`（或停写窗口文件拷贝）→ gzip → 保留最近 14 份 + 每月 1 份；
3. **备份验证**：每月随机抽 1 份备份在临时目录解压、用 `sqlite3 integrity_check` 验证可开；
4. 备份文件不进 git（.gitignore 已排除 `*.db`/`*.db.gz`）。

## 五、M4 端口接管切换预案

现有旧网关运行于生产 3000 端口。hui-api 切换采用「旁路验证 → 接管 → 可回滚」三段式：

### 阶段 1：3100 旁路验证（不动生产）

```bash
./hui-api -addr :3100        # 新服务起在 3100
curl http://127.0.0.1:3100/health
# 用测试令牌完整验证：鉴权/路由/计费/日志
```

### 阶段 2：3000 接管

```bash
systemctl stop old-gateway && systemctl start hui-api   # 接管 3000
curl http://127.0.0.1:3000/health
```

### 阶段 3：回滚（两条命令）

```bash
systemctl stop hui-api && systemctl start old-gateway
```

> 回滚前提：旧服务未卸载、其数据文件未被破坏（hui-api 验证期使用独立 db 文件，不碰旧库）。接管后旧库保留至少一个观察期，再规划数据迁移。

## 六、数据迁移（M4）

- 通用 SQL 工具 + 六表同语义列名做映射导入（见 03-数据模型与迁移.md 第三节）；
- 迁移工具与对账脚本已交付（M4-wave1，ADR-0008）：旧库绝对只读 + 幂等覆盖式同步 + 强对账；
- 迁移源用**备份副本**（而非生产库文件），旁路期零接触生产库。

## 七、正式切换 runbook（M4-wave2 实测版）

> 2026-09-04 旁路部署实测后固化。旁路环境（已就位并冒烟 7/7 PASS）：systemd 单元
> `hui-api.service`、`127.0.0.1:3100`、`/home/ubuntu/hui-api/{bin,config,data,logs}`、
> `MemoryMax=400M` + `GOMEMLIMIT=120MiB`（ADR-0009）；冒烟脚本 `scripts/deploy-smoke-server.sh`
> （`HUI_BASE` 可覆盖目标端口，接管 3000 后复用）。

### 预检清单（全部满足才开窗）

- [ ] **对账全绿**：最新备份跑 migrate 两遍报告 diff IDENTICAL（本地 `scripts/migrate-drill.ps1`）。
- [ ] **备份在手**：服务器每日备份轮转目录内当日 `.db.gz` 存在且 `integrity_check: ok`
  （cron 04:30 自动生成；目录与文件名以服务器 crontab 实测为准，本地备份副本同步拉回）。
- [ ] **窗口选择**：低峰时段（建议 04:30 备份完成后）；切换动作总耗时预估 <5min。
- [ ] **旁路健康**：`systemctl is-active hui-api` = active；冒烟 7/7 PASS（当日重跑）。
- [ ] **回滚认知**：回滚 = 两条命令（见下），RTO <30s；旧库全程零写入。

### 切换步骤（预估总耗时 <5min，每步附验证）

| 步 | 操作 | 预估 | 验证命令 |
| --- | --- | --- | --- |
| 1 | **快照**：`echo ".backup '<快照目录>/pre-hui-$(date +%F-%H%M).db'" \| sudo sqlite3 <旧库路径>`（`<旧库路径>`=生产旧库文件、`<快照目录>`=其手动快照目录，以服务器实测为准；`.backup` 为 sqlite3 在线只读备份 API，不碰源库） | <5s | `ls -l <快照目录>/pre-hui-*.db`；`PRAGMA integrity_check` ok |
| 2 | **停旧网关**：`sudo systemctl stop <旧网关单元名>`（仅 stop 不 disable，保留回滚；单元名以 `systemctl list-units` 实测为准） | <3s | `systemctl is-active <旧网关单元名>` = inactive；`curl http://127.0.0.1:3000/health` 连接拒绝 |
| 3 | **最终迁移**（推荐重置目标库：`sudo systemctl stop hui-api` → 删 `data/hui-api.db` → 解压最新备份 → `migrate -legacy <备份副本> -target data/hui-api.db -report logs/migrate-report.json`） | <15s | 退出码 0；对账 18 项全 OK；报告 diff 与预检一致 |
| 4 | **改绑 3000**：config.yaml `addr` 改 `":3000"` → `sudo systemctl restart hui-api` | <5s | `ss -tln \| grep :3000` 由 hui-api 进程持有；`curl http://127.0.0.1:3000/health` 200；`/api/status` schema=4 |
| 5 | **冒烟**：`HUI_BASE=http://127.0.0.1:3000 bash ~/hui-api/bin/deploy-smoke-server.sh <tokens.tsv>` | <60s | 7/7 PASS（含迁移令牌 `/v1/models` 200 与真实转发计费复核） |
| 6 | **观察 30min**：`journalctl -u hui-api -f`；logs 表计费入账；`free -m`；错误关键字计数 | 30min | 无 panic/fatal；quota 正常入账；RSS <300MB |

> 步骤 3 必须重置目标库：对账语义前提是目标库为未上线库（ADR-0008），旁路期冒烟增量
> （少量 logs）会破坏行数对账；旁路库无真实业务数据，删除重建零损失且对账严格全绿。
> 迁移工具守卫（M4 评审补记）：目标库非空（已有业务数据）时 migrate 拒跑——须重置为
> 空库，或目标确为在用库且显式传 -allow-live-target 时才继续（防误指向在线库）。
> 步骤 2 后旧网关端口释放，步骤 4 的 restart 才能绑上 3000（若 restart 失败立即回滚）。

### 回滚路径（RTO <30s，全程旧库零写入）

```bash
sudo systemctl stop hui-api
sudo systemctl start <旧网关单元名>
curl -sf http://127.0.0.1:3000/health   # 200 即恢复
```

- 回滚前提自然成立：步骤 2 仅 stop 未 disable；hui-api 全程用独立库文件（`data/hui-api.db`），
  生产旧库只在步骤 1 被 `.backup` 只读复制过一次；`pre-hui-*.db` 快照兜底。
- 回滚后把 config.yaml `addr` 改回 `"127.0.0.1:3100"` 并 restart，恢复旁路态排查后再切换。
- 观察期结束（建议 ≥7 天稳定运行）再规划 `systemctl disable <旧网关单元名>`；旧网关二进制与数据文件
  不删除，保留完整回滚能力。
