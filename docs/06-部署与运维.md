# 06-部署与运维

> 状态：M4-wave3 修订版（2026-09-04 旁路部署落机 + 端口决策 3100 长期化，启用 runbook 见第七节）。
> 旧网关在本文档中一律中性称呼为「旧网关（legacy）」。

## 一、目标部署形态

- 单台 Linux 服务器（Ubuntu），systemd 托管单进程；
- SQLite 数据文件 + 定期备份；
- 生产监听 127.0.0.1:3100——**3100 为长期端口（用户决策 2026-09-04），不切 3000**（见第五/七节）。

## 二、交叉编译

Windows 开发机（PowerShell）：

```powershell
$env:CGO_ENABLED='0'; $env:GOOS='linux'; $env:GOARCH='amd64'
go build -trimpath -ldflags "-s -w -X main.version=<tag> -X main.commit=<sha>" -o bin/hui-api-linux-amd64 ./cmd/hui-api
go build -trimpath -ldflags "-s -w" -o bin/migrate-linux-amd64 ./cmd/migrate
```

> 纯 Go SQLite 驱动 + `CGO_ENABLED=0`，任何平台可直接交叉编译出 Linux 二进制。
> 本地与服务器双侧 MD5 校验（`Get-FileHash -Algorithm MD5` vs `md5sum`）后再用。

Linux 侧上传后：

```bash
chmod 755 hui-api-linux-amd64 && ./hui-api-linux-amd64 -version
```

## 三、systemd 单元（M4-wave2 生产实测版）

`/etc/systemd/system/hui-api.service`（旁路态，config 键位对齐 config.example.yaml）：

```ini
[Unit]
Description=hui-api LLM gateway (bypass 127.0.0.1:3100)
After=network.target

[Service]
Type=simple
User=ubuntu
WorkingDirectory=/home/ubuntu/hui-api
ExecStart=/home/ubuntu/hui-api/bin/hui-api-linux-amd64 -config /home/ubuntu/hui-api/config/config.yaml
Environment=GOMEMLIMIT=120MiB
Restart=on-failure
RestartSec=3
MemoryMax=400M
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
```

config（`/home/ubuntu/hui-api/config/config.yaml`，chmod 600；键位对齐 config.example.yaml）：

```yaml
addr: "127.0.0.1:3100"                          # 长期端口（2026-09-04 用户决策，不改绑 3000）
sqlite_path: "/home/ubuntu/hui-api/data/hui-api.db"
session_secret: "<openssl rand -hex 32，服务器端生成一次固化，不落仓库>"
```

## 四、备份策略

1. **迁移前自动备份**：进程启动执行 schema 迁移前，先对 db 文件做快照备份（`.db.gz`）；
2. **日常定时备份**：cron 每日 `sqlite3 .backup`（或停写窗口文件拷贝）→ gzip → 保留最近 14 份 + 每月 1 份；
3. **备份验证**：每月随机抽 1 份备份在临时目录解压、用 `sqlite3 integrity_check` 验证可开；
4. 备份文件不进 git（.gitignore 已排除 `*.db`/`*.db.gz`）。

### 预检清单（全部满足才开窗）

- [ ] **对账全绿**：最新备份跑 migrate 两遍报告 diff IDENTICAL（本地 `scripts/migrate-drill.ps1`）。
- [ ] **备份在手**：服务器每日备份轮转目录内当日 `.db.gz` 存在且 `integrity_check: ok`
  （cron 04:30 自动生成；目录与文件名以服务器 crontab 实测为准，本地备份副本同步拉回）。
- [ ] **窗口选择**：低峰时段（建议 04:30 备份完成后）；切换动作总耗时预估 <5min。
- [ ] **旁路健康**：`systemctl is-active hui-api` = active；冒烟 7/7 PASS（当日重跑）。
- [ ] **回滚认知**：回滚 = 流量入口切回旧网关（旧网关与其 3000 端口全程不动），RTO <30s；旧库全程零写入。

### 启用步骤（预估总耗时 <5min，每步附验证）

| 步 | 操作 | 预估 | 验证命令 |
| --- | --- | --- | --- |
| 1 | **快照**：`echo ".backup '<快照目录>/pre-hui-$(date +%F-%H%M).db'" \| sudo sqlite3 <旧库路径>`（`<旧库路径>`=生产旧库文件、`<快照目录>`=其手动快照目录，以服务器实测为准；`.backup` 为 sqlite3 在线只读备份 API，不碰源库） | <5s | `ls -l <快照目录>/pre-hui-*.db`；`PRAGMA integrity_check` ok |
| 2 | **最终迁移**（重置目标库：`sudo systemctl stop hui-api` → 删 `data/hui-api.db` → 解压最新备份 → `migrate -legacy <备份副本> -target data/hui-api.db -report logs/migrate-report.json`） | <15s | 退出码 0；对账 18 项全 OK；报告 diff 与预检一致 |
| 3 | **流量入口切换**：公网入口（80/443 反代/域名等，形态以服务器实测为准）由旧网关（3000）切至 `127.0.0.1:3100`；如有直连 3000 的客户端同步改 base_url 至 3100。旧网关本步不动 | <60s | 入口探活 `curl -sf http://127.0.0.1:3100/health` 200；`ss -tln` 确认 3100 由 hui-api 持有、3000 仍由旧网关持有 |
| 4 | **冒烟**：`HUI_BASE=http://127.0.0.1:3100 bash ~/hui-api/bin/deploy-smoke-server.sh <tokens.tsv>` | <60s | 7/7 PASS（含迁移令牌 `/v1/models` 200 与真实转发计费复核） |
| 5 | **观察 30min**：`journalctl -u hui-api -f`；logs 表计费入账；`free -m`；错误关键字计数 | 30min | 无 panic/fatal；quota 正常入账；RSS <300MB |

> 步骤 2 必须重置目标库：对账语义前提是目标库为未上线库（ADR-0008），旁路期冒烟增量
> （少量 logs）会破坏行数对账；旁路库无真实业务数据，删除重建零损失且对账严格全绿。
> 迁移工具守卫（M4 评审补记）：目标库非空（已有业务数据）时 migrate 拒跑——须重置为
> 空库，或目标确为在用库且显式传 -allow-live-target 时才继续（防误指向在线库）。
> 步骤 3 是唯一「生产生效」动作且可瞬时回切（入口切回旧网关即可）；旧网关全程不动，
> 原计划「停旧网关释放 3000」步骤随端口决策一并取消。

### 回滚路径（RTO <30s，全程旧库零写入）

```bash
# 流量入口切回旧网关（反代/域名指回 3000；直连客户端 base_url 改回旧地址），即恢复服务
curl -sf http://127.0.0.1:3000/health   # 200 即恢复
# 可选加固（排查期建议）：sudo systemctl stop hui-api
```

- 回滚前提自然成立：旧网关全程未停未 disable、其 3000 端口持续持有；hui-api 全程用独立
  库文件（`data/hui-api.db`），生产旧库只在步骤 1 被 `.backup` 只读复制过一次；
  `pre-hui-*.db` 快照兜底。
- 回滚后流量回到旧网关，hui-api 保持旁路态（127.0.0.1:3100）继续排查，问题闭环后重走本节 runbook。
- 观察期满（建议 ≥7 天稳定运行）执行收尾：`sudo systemctl disable --now <旧网关单元名>`，
  3000 随之闲置；旧网关二进制与数据文件不删除，旧库转只读回溯与应急，不再承载业务
  （旧网关停用后不再产生增量，分叉就此冻结）。

### 数据分叉警示（启用 3100 为生产前必读）

- **旁路库数据落后旧库 ≤24h**（cron 备份周期）：旁路库内容来自最近一次备份副本，备份
  之后旧库新增的业务数据（充值/兑换/计费日志）不在其中。
- **启用前必须执行最终迁移**（步骤 2）：重置旁路库为空库重跑 migrate——秒级幂等；守卫
  已就位：目标库非空时拒跑，须空库或显式 `-allow-live-target`（防误指向在用库）。
- **窗口内增量分叉**：最终迁移完成到流量入口切换之间，旧网关仍在服务、旧库仍在增长，
  这段增量不会自动进入 hui 库——因此步骤 2 与步骤 3 应在同一低峰窗口内连续完成
  （预估总耗时 <5min）；窗口内旧库如有新增业务数据，事后人工对账补齐。
- **入口切换后旧库应冻结**：观察期收尾即停用旧网关单元（见回滚路径末条），避免旧网关
  继续接收流量、旧库继续累积增量导致两库彻底分叉。
