# ADR 0004 — 计费引擎落地：expr 选型、口径唯一化与 tier 单层语义

> 状态：已接受 | 日期：2026-09-02 | 决策人：hui-api 作者

## 背景

M1-wave3 落地 docs/04 计费设计时，四个问题需要定案：

1. 表达式引擎的来源：docs/04 设计稿写「自研实现白名单运算（四则、比较、tier/round 等）」，自研求值器的覆盖面、安全性与维护成本需要评估；
2. tiered_expr 的变量口径与 quota 换算存在两种数学等价的表述（原始 tokens × $/M 单价 vs 百万 tokens × $ 单价），浮点路径与断言值必须唯一化，否则注释、公式、测试三方漂移；
3. `tier()` 函数语义的分层：完整阶梯定价（按用量/上下文分档选择表达式）依赖尚不存在的配置面；
4. 未配价模型的拒绝语义：设计稿写「HTTP 4xx」，但价格缺失的归因（服务端配置问题 vs 客户端过错）决定 4xx 内的具体选择。

约束：零 CGO（ADR 0001）；宁可拒绝请求不可错扣一分（docs/04）；生产环境四条实测账单样例可作为公式口径的裁决事实源。

## 决策

### 1. 表达式引擎引入 github.com/expr-lang/expr

- compile/run 两阶段：`expr.Compile` 产物按表达式文本缓存（RWMutex + 双检），同一表达式并发求值复用编译结果；
- 启动校验升级为「编译 + 零用量试求值」：档位名错误、类型错误等运行期失败在启动时即暴露（价单损坏宁可启动失败，不带着坏价单服务）；
- 自定义 `tier` 函数经 `expr.Function` 注册进求值环境，未知标识符默认报错（白名单效果）。

### 2. 口径唯一化：变量 = 原始 tokens 数，表达式值 = micro-USD

- `p` = 纯输入 tokens（input − cache_read）、`c` = 输出 tokens、`cr` = 缓存读 tokens；
- 单价由表达式内系数表达（`p * 0.15` 即 $0.15/百万 tokens），表达式值单位 micro-USD；
- `quota = round(expr × 500000 / 1e6)`（即 ÷2），四舍五入用 Go `math.Round`（半数远离零）；
- **cache 拆分防重复计费**：relay.Usage 的 CacheReadTokens 已计入 PromptTokens，计费拆分时二者相加还原 input，缓存部分只计一次；
- 口径锚点由黄金测试集固化（四条实测账单逐位断言），任何口径改动必须在注释、公式因子、测试断言三处同步且全量跑黄金测试。

### 3. tier("base", expr) 本波为单层语义

- 本波取第二个参数表达式的值（base 档唯一），`tier("gold", ...)` 等未定义档位在启动试求值时即报错；
- 多层阶梯（按用量/上下文分档选择表达式）defer 到管理面配置就绪后扩展，表达式格式向后兼容（现有 `tier("base", e)` 是未来 `tier` 分档的一种特例）。

### 4. 未配价映射 HTTP 503 model_not_priced，余额不足映射 403

- 价格缺失/价格配置不可用是**服务端配置问题**，客户端无法通过修改请求修正，503 + 语义 code 比 4xx 更真实归因；错误信息不含内部细节（不回显具体缺哪个键）；
- 令牌余额不足以预扣冻结是**客户端过错**（充值即可修正），403 `insufficient_quota`；
- 两种拒绝均无副作用（不冻结、不落请求日志的计费字段）。

### 5. 价格查找顺序与不可变快照

- 查找顺序：options `billing_setting.billing_mode` 显式声明 > `ModelRatio` 隐式 classic > 内置 prices.json（go:embed + 启动校验）> `ErrUnpriced`；配置声明不完整（声明了模式但缺配套值）视为未配价——拒绝服务优于按残缺配置错扣；
- `LookupPrice` 返回不可变 `ModelPrice` 快照，单请求生命周期内预扣与结算复用同一份，配置热更不影响在途请求的口径一致性；
- GroupRatio 回退：请求组未配置 → default 组值 → 1.0。

## 备选方案（含被拒绝理由）

1. **自研白名单求值器（设计稿原案）**
   - 被拒：四则/比较/tier/round 的解析器与求值器是数百行级造轮子，覆盖面不如 expr-lang（字符串/条件/数学函数全齐），且安全审计面反而更大；expr-lang 成熟、纯 Go、零 CGO，符合 ADR 0001。
2. **变量传百万 tokens 数（值=美元，quota = 值 × 500000）**
   - 被拒：与任务规格公式因子（×500000/1e6）不符，且四条实测账单数值在原始 tokens 口径下直接对齐（371253×0.15+3248×0.5=57311.95 → 28656）；两种表述虽数学等价，规格与事实源都指向前者。
3. **本波实现完整 tier 阶梯**
   - 被拒：分档依据（用量/上下文阈值与档位名）没有配置面承载，M2 管理面 API 未落地，先实现只会有硬编码；YAGNI。
4. **未配价 400/422**
   - 被拒：语义归因错误——4xx 暗示客户端请求可修正，而配价是运营动作；且 400 已被「缺 model/坏 JSON」占用，混用会让客户端排障混淆。

## 后果

- 正面：配置错误启动即暴露（试求值）；计费口径有唯一锚点且被黄金测试固化；缓存部分防重复计费；在途请求免热更漂移；拒绝语义归因清晰。
- 负面：引入新依赖 expr-lang（纯 Go、无传递性 CGO 风险，可接受）；多层 tier 待扩展（已保证表达式格式向后兼容）；503 对习惯 4xx 的客户端略反直觉（语义 code 弥补，docs/05 错误码表已注明）。
- 执行要求：任何计费口径改动必须全量跑黄金测试集（`go test ./internal/billing/ -run TestGolden`）；新增表达式能力（如多层 tier）必须同步 prices.json 的零用量试求值校验；tiered_expr 永不叠乘 group_ratio（classic_ratio 与 per_call 叠乘）——该差异由 docs/04 与黄金样例固化。
