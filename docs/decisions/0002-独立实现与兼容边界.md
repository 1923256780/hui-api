# ADR 0002 — 独立实现与兼容边界（clean-room）

> 状态：已接受 | 日期：2026-09-02 | 决策人：hui-api 作者

## 背景

hui-api 服务于「替换既有自托管网关、迁移存量数据」的场景。这里有三个相互拉扯的诉求：

1. **法律与工程独立**：不能基于任何同类网关的源码做修改或衍生；
2. **平滑迁移**：用户已有数据库与使用习惯，希望数据可导入、操作概念可衔接；
3. **可维护性**：仓库必须能向任何第三方证明其独立来源。

## 决策

### 1. clean-room 纪律

- 任何会话、任何贡献者**不得阅读其他同类 LLM 网关的源码**；
- 功能规格只来自两个来源：**公开文档**（官方文档、公开讨论）与**黑盒行为观察**（作为用户实际操作其公开接口所得）；
- 观察所得写成「需求」文档（本 docs/ 体系），实现完全按自家架构独立编写。

### 2. schema 兼容边界

- 六表列名与行业通用语义**同名同义**（如 `key_hash`/`budget_duration`/`tpm_rpm`/`tags`、`base_url`/`priority`/`weight`/`quota` 等）；
- 目的不是模仿某产品，而是采用行业通用的字段语义，使用户数据可用**通用 SQL 工具**直接映射导入；
- 不保证与任何具体产品 100% 兼容；迁移以 docs/03 的六表映射为准，由官方迁移工具（M4 交付）承载。

### 3. 竞品匿名纪律

- 仓库内任何文档/注释/commit 信息**不得出现其他同类项目的名称**（含影射）；
- 词表维护于 `.github/competitor-words.txt`，CI 用 grep 全量扫描拦截（扫描排除词表文件与检查脚本自身）；
- 该纪律同时保护仓库来源的独立性证明——对外描述项目时永远只描述 hui-api 自己的能力。

## 备选方案（含被拒绝理由）

1. **直接 fork 某同类网关**
   - 被拒：许可义务与原始项目维护负担全盘继承；无法满足独立设计目标；来源关联清晰可见，与本项目动机相悖。
2. **完全无兼容目标（纯原创 schema）**
   - 被拒：用户存量数据迁移成本显著上升，放弃「平滑替换」这一核心场景价值。
3. **读竞品源码学习但重写实现**
   - 被拒：污染 clean-room 状态，衍生嫌疑无法自证，直接违反本 ADR 第 1 条。

## 后果

- 正面：来源干净、法律风险低；架构完全自主，不受既有实现的历史包袱约束；「文档先行」的开发模式让设计决策可追溯。
- 负面：前期开发速度略慢（需求要靠公开文档与黑盒观察自行拼合）；行为细节可能与用户习惯有差异，需靠文档与迁移工具弥合。
- 执行要求：AI 会话上下文中若意外混入同类网关源码，会话必须终止重开；本纪律由 CI 与评审共同执行。
