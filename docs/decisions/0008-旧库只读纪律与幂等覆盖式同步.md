# ADR 0008 — 旧库只读纪律与幂等覆盖式同步（迁移工具）

> 状态：已接受 | 日期：2026-09-04 | 决策人：hui-api 维护者

## 背景

M4 端口接管切换前，需把旧网关（下称"旧库"）SQLite 六表数据一次性迁入 hui 库（internal/migrate + cmd/migrate）。约束与风险：

- 旧库是生产数据的唯一真本，迁移期间旧网关可能仍在服务——任何写旧库的行为（哪怕误操作 UPDATE）都不可接受，且事后无法从 hui 侧察觉；
- 两套计费口径不同：旧库 classic 计费无 /1e6 环节（mr 数值内嵌比例），hui 计费含 500000/1e6 环节，ModelRatio 直接照抄必然错账；
- 令牌鉴权唯一依据是 key_hash（SHA-256 hex），迁移侧若自行实现哈希存在口径漂移风险；
- 演练必须可重复（清库重跑 N 遍结果一致），否则无法证明切换日操作的确定性；
- 旧库存在无法自动映射的数据（渠道多组信息、model_mapping、换皮 options、非 consume 日志），处置策略必须显式。

## 决策

- **旧库绝对只读（双层防御）**：internal/store.OpenReadOnly——DSN `file:...?mode=ro`（SQLite 层拒绝写）+ 连接建立后 `PRAGMA query_only=1`（引擎层兜底），只读池限 2 连接。测试对该池执行 INSERT/UPDATE/CREATE 均断言报错（attempt to write a readonly database）且文件逐字节无污染。迁移工具的旧库读取只有这一条通道，代码里不存在第二条路径。
- **幂等覆盖式同步（自然键 upsert）**：全部写入 `ON CONFLICT(自然键) DO UPDATE`——users.username / tokens.key_hash / channels.id / redemptions.key / logs.id / options.key。清库重跑 N 遍与首遍结果逐字节一致；报告完全确定性（无时间戳、切片稳定排序）。自然键撞车（不同 id 同键的脏数据）按自然键覆盖，语义为"最后一次迁移赢"；覆盖列仅限迁移归属列（预算、aff、totp 等运行时列不被旧值覆盖）。
- **变换显式硬失败**：未知渠道类型/状态、非 bcrypt 密码、非 envelope 格式的 param_override、未知令牌状态等一律拒绝该行并计入报告（行失败不阻塞其余行迁移），绝不静默丢弃或猜测。守卫（QuotaPerUnit≠500000）与对账不等使整体 exit 非零。
- **key_hash 复用 gateway.HashKey**：迁移侧不写任何哈希逻辑，令牌明文 = `"sk-" + 旧库 48 位`，哈希与运行时鉴权同源，杜绝口径漂移。
- **ModelRatio 换算方向 legacy×2**：旧 classic `quota=(p+c·cr)·mr_l·gr`，hui `quota=(p+c·cr)·mr_h·gr·500000/1e6`；令两式对同一账单相等 ⇒ mr_h=mr_l×2。三例黄金锚定（旧库真实账单：deepseek-v4-flash 旧账 85 / glm-5.3-flash tiered_expr 766 / qwen3.8-flash 14）固化于 transform_test（TestModelRatioGoldenAnchoring），换算后逐一复现旧账。换算范围取启用渠道模型最小集，旧库缺价模型入报告缺口（不虚构价格）。
- **强对账内置**：迁移完成后逐表比对 行数 / SUM(quota) / SUM(used_quota)（旧侧只读 vs 新侧，含 consume/topup 分列与 unlimited 计数，共 13 项指标）+ options 键值逐项一致性，任一不等 exit 1 并输出差异明细。对账语义前提：目标库为未上线库（切换窗口内），运行期增删行会破坏比对。
- **报告即审计**：-report 输出 JSON（各表读/迁/失败计数、行失败明细、未迁 options 清单、model_mapping 缺口、ModelRatio 换算明细、对账逐项结果），失败路径同样落盘供排查。

## 备选方案（含被拒绝者及理由）

1. **SQLite ATTACH 跨库 SQL 直迁**（读旧库写 hui 一条 INSERT..SELECT）
   - 被拒理由：bcrypt 守卫、envelope→ops 变换、类型映射、计费换算全部塞进 SQL 不可单测、不可读；ATTACH 只读语义依赖连接参数拼写，纪律性弱于独立只读连接 + 显式测试。
2. **一次性 INSERT（假设目标恒为空库）**
   - 被拒理由：演练要求清库重跑多遍、切换日可能多次执行；INSERT 在重复执行时撞唯一索引即失败，无幂等；"清了再跑"依赖人工纪律而非工具保证。
3. **ModelRatio ÷2（按"hui 单价数值更大"的直觉）**
   - 被拒理由：黄金锚定反证——÷2 后同账单算出 21≠85；×2 才逐例复现旧库账单。方向必须由账单锚定，不由直觉决定。
4. **迁移期写旧库打标记（防重复迁移/记录水位）**
   - 被拒理由：幂等 upsert 使重复迁移本就无害，无需水位；写通道的存在本身就是风险，与只读纪律冲突。

## 后果

- 正面：旧库零风险（只读双层 + 写失败测试证明）；演练/切换可无限次重跑（幂等 + 确定性报告，两遍 diff 可自动断言）；错账风险被黄金锚定与强对账双重拦截；变换规则全部纯函数化、正反例全覆盖。
- 负面：目标库必须是未上线库（对账语义前提，切换窗口内成立）；channels 多组信息与 model_mapping 在 hui 无对应列，只能丢弃并入报告人工复核；-export-tokens 产物含令牌明文（本地敏感文件，用后即删）。
- 中性/执行要求：改动 internal/migrate 必须重跑黄金锚定与幂等测试（`go test ./internal/migrate/ -race`）；新增变换规则必须先加反例测试；对账不等永远视为失败（不存在"可忽略的差异"）；生产切换前必须完成本地演练 2 遍 + 对账 + 冒烟（scripts/migrate-drill.ps1）。
