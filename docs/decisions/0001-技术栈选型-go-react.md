# ADR 0001 — 技术栈选型：Go + React

> 状态：已接受 | 日期：2026-09-02 | 决策人：hui-api 作者

## 背景

hui-api 的核心交付形态是「单二进制 + SQLite，零外部依赖」，目标用户是个人开发者与小团队，部署环境以单台 Linux 服务器为主，开发环境在 Windows。需要选定后端语言、Web 框架、ORM、SQLite 驱动与前端方案。

关键约束：

1. 交叉编译：开发机 Windows，生产 Linux，必须一条命令产出目标二进制；
2. 零 CGO：避免交叉编译时对 C 工具链的依赖；
3. 单二进制：前端资源要嵌入二进制；
4. 低内存：服务器小规格（systemd MemoryMax=400M 档位）也要稳定运行。

## 决策

| 项 | 选型 | 理由 |
| --- | --- | --- |
| 后端语言 | Go 1.23+ | 单二进制、交叉编译、低内存、并发模型适合 IO 转发 |
| Web 框架 | Gin | 路由性能与中间件生态成熟，学习成本低 |
| ORM | GORM | 迁移与仓储模式支持完善 |
| SQLite 驱动 | glebarez/sqlite（纯 Go） | 免 CGO，交叉编译零负担，SQLite 场景性能足够 |
| 前端 | React 18 + Vite | 函数组件 + hooks，构建快 |
| 嵌入 | go:embed | 前端 dist 打进二进制，交付物只有一个可执行文件 |

## 备选方案（含被拒绝理由）

1. **Node 全栈（Express/Nest + React）**
   - 被拒：交付需要 Node 运行时或复杂打包（pkg/bundle），与「单二进制零依赖」目标冲突；SQLite 原生绑定链路同样存在原生模块问题。
2. **Python FastAPI + React**
   - 被拒：分发依赖解释器与虚拟环境管理，长驻网关进程的内存与 GC 行为不如 Go 可控；高并发流式转发场景吞吐偏低。
3. **Rust（Axum + Leptos/Yew）**
   - 被拒：开发效率与迭代速度不匹配个人项目节奏；ORM/迁移生态成熟度不足，计费表达式引擎等自研组件会进一步拉长周期。
4. **SQLite 驱动用 mattn/go-sqlite3（CGO）**
   - 被拒：引入 CGO 后 Windows→Linux 交叉编译需要 C 交叉工具链，违背零负担交叉编译约束。

## 后果

- 正面：`CGO_ENABLED=0` 一条命令交叉编译；前端构建产物嵌入后交付物只有一个文件；SQLite 单文件备份运维简单。
- 负面：纯 Go SQLite 驱动在高并发写场景吞吐低于 C 实现——按单机个人/小团队规模评估可接受；React 管理台构建链路引入 Node 开发依赖（仅开发期需要，部署机不需要）。
- 中性：GORM 对复杂 SQL 的表达力一般，存储层按仓储模式封装，复杂查询下沉到手写 SQL。
