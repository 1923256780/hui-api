# ADR 0006 — 商业化开关：options 白名单、敏感值哨兵脱敏与默认关不落库

> 状态：已接受 | 日期：2026-09-03 | 决策人：hui-api 维护者

## 背景

M3-wave1 商业化扩展（注册/SMTP 邮件/Turnstile 人机校验/OAuth 第三方登录/EPay 与 Stripe 支付/邀请返利/充值）一次性引入十余个可写配置命名空间，其中 `smtp.password`、`epay.secret_key`、`stripe.secret_key`、`stripe.webhook_secret`、`oauth.*_secret` 等直接承载凭据。运行轨配置端点 PUT /api/option 必须同时满足：

1. 防误写：不得覆盖 `schema_version` 等内部键，也不允许业务代码通过接口注入任意键；
2. 防泄密：敏感凭据不得出现在 GET 响应、前端状态或任何日志里；
3. 防误覆盖：前端把脱敏回显原样提交回来时，不得用哨兵字符串冲掉真实密钥；
4. 部署面干净：未启用商业化功能时不应有任何隐式行为来源。

约束：单二进制、零新依赖、root-only 管理面、options 单表 KV（SQLite）。

## 决策

- **写路径白名单前缀制**（`allowedOptionKey`，internal/api/option.go）：可写键限定为模块命名空间前缀——`relay.*`、`billing_setting.*`、`hooks.*`（M2），M3 新增 `smtp.*`、`register.*`、`oauth.*`、`turnstile.*`、`epay.*`、`stripe.*`、`aff.*`、`topup.*`——外加与 gateway/billing 包常量同源的行业通用精确键（模型倍率、限流键）。读路径（GET）不做白名单过滤以便诊断；写路径任一键非法则整体拒绝、不做部分写入。值长度上限 2048。落库成功即触发 `config.Runtime.Reload()` 热生效。
- **敏感值出口脱敏**：`isSensitiveOptionKey` 按键名含 `password` 或 `secret` 子串（不区分大小写）判定；GET 返回时值替换为哨兵 `"******"`，库内明文不变——脱敏只发生在出口。
- **哨兵跳过（保持旧值语义）**：PUT 收到值为 `"******"` 的键，校验先行（哨兵键同样必须过白名单），随后整体剔除不落库，即「保持旧值」。该语义与前端实现解耦：前端把脱敏回显原样提交回来是幂等无害的，服务端跳过是最终防线。
- **默认关=不落库**：全部商业化开关取值形如 `rt.GetBool(OptionKeyRegisterEnabled, false)`——缺省即关。options 表只存管理员显式写入的行：未配置的开关不产生任何数据库行，功能关闭的判定来源唯一（代码内缺省值），不存在「代码缺省 vs 库内预置行」两处事实源。启用某功能 = 管理员显式写入对应键。

## 备选方案（含被拒绝者及理由）

1. **写路径全开放（按需写任意键）**
   - 被拒理由：内部键（schema_version 等）可被误改；任意键注入让 options 表成为绕过 schema 的后门，行为不可审计。
2. **敏感键加密落库（AES + 主密钥）**
   - 被拒理由：单二进制无 KMS，主密钥只能落盘或硬编码，加密提供的增量保护有限；root-only 面已隔离读取，出口脱敏已覆盖主要泄露面。加密反使诊断与迁移复杂。
3. **哨兵语义移到前端（已脱敏字段不提交）**
   - 被拒理由：前端任一处遗漏即把真实密钥清空；服务端跳过是防误覆盖的最终防线，且与客户端实现解耦（API 层幂等，curl 原样回放也安全）。
4. **默认开 + 预置 options 默认行**
   - 被拒理由：注册/支付默认暴露有安全风险；预置行造成行为来源分裂（改代码缺省值对已有部署无效，反而引入「删行才生效」的反直觉运维）。
5. **敏感键细粒度显式清单**
   - 被拒理由：`password`/`secret` 子串匹配覆盖现有与未来键（`stripe.webhook_secret` 等自然命中），显式清单每加一个键就要同步维护，漏维护即泄露。

## 后果

- 正面：新增商业化配置键零后端改动（落在既有前缀内即可写）；凭据不出现在任何 GET 响应/前端状态/日志中；未启用功能的部署 options 表为空，行为来源唯一。
- 负面：新命名空间需修改 `allowedOptionKey`（改动集中一处，可接受）；键名若不含 `password`/`secret` 字样则不会被脱敏，命名纪律成为依赖。
- 中性/执行要求：新增 options 键必须落白名单；敏感凭据键命名必须包含 `password` 或 `secret`；改键名需评估 `isSensitiveOptionKey` 是否仍命中；商业化开关的新增缺省值必须为关（false/空）；凡动 option 写路径需回归 `register_test.go` 的脱敏与哨兵用例。
