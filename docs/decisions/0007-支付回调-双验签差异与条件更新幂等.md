# ADR 0007 — 支付回调：双验签差异、金额逐位校验与条件更新幂等

> 状态：已接受 | 日期：2026-09-03 | 决策人：hui-api 维护者

## 背景

M3-wave2 充值接入双网关（EPay 易支付协议 / Stripe Checkout），回调是资金入账的唯一入口，必须抵御四类风险：重复通知（网关重发）、并发回调（同一订单两路通知同时到达）、参数篡改（降额/跨网关混淆/币种混淆）、伪造回调（无凭据构造请求）。两个协议的验签能力不对等：

- EPay 异步通知：MD5 签名（协议规定），无时间戳、无防重放原语；
- Stripe webhook：`Stripe-Signature` 头 `t=...,v1=...`，HMAC-SHA256 带时间窗。

回调端点是公开路由（支付网关服务器无会话，验签即鉴权），`return` 浏览器回跳同样公开。入账、日志、邀请返利必须要么全成功要么全不发生。

## 决策

- **验签照协议能力分别实现，弱协议以纵深补偿**（internal/payment）：EPay 按协议参数按键排序、剔除 `sign`/`sign_type` 与空值、拼接 secret 计算 MD5 与通知内 `sign`（hex）比对；承认 MD5 弱——secret 保密是唯一前提，因此金额逐位校验与 secret 的敏感脱敏（ADR-0006）构成纵深。Stripe 按官方口径 `HMAC-SHA256(secret, "{t}.{payload}")` 与头中每个 `v1` 恒时比较（`hmac.Equal`，任一匹配即通过），且 `|now - t| ≤ ±5min` 防重放（`DefaultWebhookTolerance`）。
- **金额逐位校验在结算事务内**（`settleTopupOrder`）：查单后依次校验 `o.Gateway != gateway`（防跨网关混淆）、币种 `EqualFold`（防币种混淆）、`o.AmountCents != moneyMinor`（防降额攻击）。金额一律以 minor units（分/美分）整数流转；EPay 侧 `parseMoneyToMinor` 对 `money` 字符串逐位解析，不走浮点。
- **幂等 = 条件 UPDATE 单向状态机**：`UPDATE topup_orders SET status=paid WHERE id=? AND status=pending`，`RowsAffected=0` 即已结算过，幂等跳过（不重复入账、不重复返利，调用方仍回成功应答）。订单过期 worker（M3-wave4）的关单同为条件 UPDATE `WHERE status=pending AND created_time < cutoff`：支付回调与关单在 SQLite 单写池内串行化，先到先得——回调先到则关单 0 行受影响，关单先到则回调金额校验后置 paid 被状态条件拒绝，二者共同构成 pending→paid / pending→expired 的单向状态机，无中间态。
- **aff 返利同事务**：买家余额入账、topup 对账日志、邀请人 `quota` 与 `aff_history_quota` 累加、aff 返利日志全部在 `st.Write.Transaction` 内；任一步失败整体回滚（网关收到 fail 会重试）。邀请人已被删除（UPDATE `RowsAffected=0`）时跳过返利但不阻塞买家入账。返利比例在事务开始前快照（`aff.rebate_percent`），与结算原子性解耦。
- **return 端点不承担安全边界**：`EpayReturn` 仅 302 到 `/console/topup?order=<order_no>`，不做任何状态变更；真实入账唯一路径是 notify 验签事务。前端据订单号查 `/api/user/topup/orders`（登录态所有权作用域）展示状态——展示链路与资金链路彻底分离，浏览器侧参数可伪造但只能影响自己的视图。
- **应答语义照网关切分**：EPay 纯文本 `success`/`fail`（网关重试依据）——验签失败/缺单号/金额非法/结算错误回 `fail` 触发重试，非成功 `trade_status` 回 `success` 确认已知悉防重发但不入账。Stripe 验签失败/载荷非法/订单不符回 4xx 触发官方重试，`checkout.session.completed` 之外的事件类型回 200 确认忽略。Stripe 下单先创建 Checkout Session 成功再落库，会话创建失败不产生孤儿 pending 单。

## 备选方案（含被拒绝者及理由）

1. **为 EPay 自建更强签名协议（HMAC + 时间戳）**
   - 被拒理由：签名方式由网关方规定，改协议即无法对接市面易支付网关，违背接入目标。
2. **回调先落 pending 事件表再异步结算**
   - 被拒理由：单机 SQLite 同事务结算已原子，事件表引入对账复杂度（两阶段状态）而无并发收益；网关重试语义（fail 后重发）已覆盖瞬时故障。
3. **幂等以 `trade_no` 唯一索引保障**
   - 被拒理由：`trade_no` 是网关侧标识，条件 UPDATE 已对重发幂等；对 `trade_no` 建唯一索引反而在网关测试回调复用同一 `trade_no` 于不同订单时误拒。
4. **return 端点也做验签 + 入账（双通道）**
   - 被拒理由：浏览器回跳参数可被用户伪造，等价于把入账边界暴露给客户端；return 参与状态变更还会造成 notify/return 竞态双入账风险，幂等条件虽可挡住，但边界混乱不可审计。
5. **金额校验用浮点比较（`fabs(money - order) < ε`）**
   - 被拒理由：浮点误差是降额攻击的载体（0.01 级差异被 ε 吞掉）；minor units 整数全等比较语义清晰。

## 后果

- 正面：重复通知/并发回调/跨网关混淆/降额攻击/伪造签名全路径有 httptest 覆盖（含并发幂等用例）；订单状态机单向、无中间态、可断言；两网关共享一个结算事务，新增网关只需补验签函数。
- 负面：EPay MD5 是接受的风险——secret 泄露即验签失守（金额校验只防降额不防伪造金额相同的单），运维上 `epay.secret_key` 必须妥善保管（其在敏感脱敏覆盖内，不出现在任何出口）。
- 中性/执行要求：新增支付网关必须提供验签函数并接入 `settleTopupOrder` 共享结算；金额一律 minor units 整数；回调端点保持公开无会话（验签即鉴权）；`return` 类端点永久禁止状态变更；凡动结算路径需回归 `order_test.go` 的并发幂等与金额校验用例。
