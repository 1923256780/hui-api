# 01-架构总览

> 状态：**活文档**。模块边界、目录结构、数据模型变化时必须同步本文，并在 `decisions/` 新增 ADR。

## 一、设计原则

1. 单二进制 + SQLite：部署面收敛到「一个进程 + 一个文件」；
2. 主链路最短：转发路径上只做必须的事，重活走异步旁路；
3. 可对账优先：任何一次扣费都能从日志表还原计算依据；
4. 失败可见：渠道/令牌/计费异常必须有结构化日志与状态沉淀。

## 二、目标架构：10 个设计点

### 1. Deployment 作为一等实体

版本号、监听地址、数据目录、备份策略、健康探针作为显式的部署配置项集中管理，而非散落在代码各处。二进制自带 `-version` 输出构建信息，供切换预案与运维核对。

### 2. 双协议 relay

统一转发内核对外暴露两种协议面：

- OpenAI 兼容：`/v1/chat/completions`（含流式）；
- Anthropic Messages：`/v1/messages`（含流式）与 `/v1/messages/count_tokens`。

两种协议在内部归一为统一请求描述（模型、消息、采样参数、流标记），响应侧再按入口协议还原。协议适配层与转发层解耦，适配层不做业务决策。

### 3. 渠道路由与熔断

多渠道按优先级 + 权重调度；同一渠道连续失败达到阈值即熔断，进入半开探测后恢复。渠道状态（启用/禁用/熔断中）持久化，重启不丢失熔断现场。

### 4. billing 计费内核

三模式计费（classic_ratio / tiered_expr / 按次）、预扣费 + 多退少补、流中断全额退款、未配价硬拒绝。计费是独立内核模块，relay 只调用、不感知细节。详见 `04-计费与配额设计.md`。

### 5. store 统一存储层

GORM + glebarez 纯 Go SQLite 驱动。六表模型（channels/tokens/users/redemptions/options/logs）集中定义，版本化迁移框架管理 schema 演进。所有写操作经存储层，禁止散落裸 SQL。

### 6. hook 异步旁路

审计、通知、回调类动作走异步旁路队列，失败重试但不阻塞转发主链路，也不影响响应时延。旁路消息带幂等键，重复投递不产生重复副作用。

### 7. 配置双轨热更

配置分两轨：

- 启动轨：环境变量/启动参数，仅进程启动时读取（端口、数据目录等部署面）；
- 运行轨：options 表，管理面修改后热加载生效（渠道参数、计费配置、开关类）。

运行轨变更通过版本号/更新时间感知，热更不需要重启进程。

### 8. 令牌体系

令牌明文只在创建时返回一次，库内只存 SHA-256 的 `key_hash`；支持预算周期、有效期、TPM/RPM 限流、标签分组。鉴权走哈希查找，不暴露明文比对接口。

### 9. 兑换码与用户体系

兑换码批量生成、一次核销、额度入账可追溯；用户余额独立于令牌预算，支持按用户维度审计。

### 10. 可观测与对账

每次请求落 logs 表：协议、模型、渠道、令牌、耗时、quota 上下文。计费结果可由 logs 反向重算验证（对账）。结构化日志输出到 stdout，交给 systemd 收集。

## 三、目录结构（目标态）

```
cmd/hui-api/          入口与依赖装配
internal/relay/       双协议适配与转发管道
internal/channel/     渠道池、调度、熔断
internal/billing/     计费内核
internal/store/       GORM 模型、迁移、仓储
internal/config/      双轨配置与热更
internal/hook/        异步旁路
web/                  React 管理台（go:embed 嵌入）
```

> M0 阶段仅存在 cmd/hui-api；上表是目标态，随里程碑逐波落地。落地时必须回写本文。

## 四、请求生命周期（目标态）

```
客户端 → 鉴权(key_hash) → 令牌限流(tpm/rpm) → 模型解析
      → 计费预扣(estimate) → 渠道调度(优先级/权重/熔断)
      → relay 转发 → 响应还原(按入口协议) → 计费结算(多退少补)
      → 日志落库(logs) → 异步旁路(hook)
```
