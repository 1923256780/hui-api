# 04-计费与配额设计

> 状态：**已落地（M1-wave3 计费内核，M2-wave3 兑换码与预算窗口 + 流中断部分结算，2026-09-03，`internal/billing`）**。计费是 hui-api 的可信底线：宁可拒绝请求，不可错扣一分。落地口径与设计稿的差异处均以「落地」标注，取舍见 ADR 0004；公式实测见第七节，兑换码与预算窗口见第八节。

## 一、quota 单位

- 整数计费单位，**500000 quota = $1**（`model.QuotaPerDollar`）；
- 价格配置以「每百万 tokens 的美元单价」表达，落库与结算统一换算为 quota；
- 中间过程允许浮点，产出必须四舍五入为 quota 整数（Go `math.Round`，半数远离零）。

## 二、三种计费模式

### 1. classic_ratio（倍率模式）

落地公式：

```
quota = round((input_tokens + completion_tokens × completion_ratio)
              × model_ratio × group_ratio × 500000 / 1e6)
```

- `model_ratio` 即该模型每百万输入 tokens 的美元单价；`completion_ratio` 是**输出价相对输入价的倍数**（缺省 0，即输出不计费）；
- 叠乘 `group_ratio`（组倍率，见本节第 4 点）；
- 适配大多数模型的简单线性计价；
- 倍率配置存于 options 运行轨（`ModelRatio` / `CompletionRatio`），支持热更。

### 2. tiered_expr（表达式模式）

落地口径（ADR 0004，与设计稿的差异点）：

- 表达式引擎落地引入 **github.com/expr-lang/expr**（非设计稿的自研白名单求值器）：compile/run 两阶段，编译结果按表达式文本并发安全缓存，启动校验含零用量试求值；
- **变量为原始 tokens 数**（非单价）：`p` = 纯输入 tokens（= input − cache_read）、`c` = 输出 tokens、`cr` = 缓存读 tokens；单价由表达式内系数表达（如 `p * 0.15` 即 $0.15/百万 tokens）；
- 表达式值单位为 micro-USD，`quota = round(expr × 500000 / 1e6)`；
- **cache 拆分防重复计费**：relay.Usage 的 CacheReadTokens 已计入 PromptTokens，计费拆分时 `p = input − cache_read`、`cr = cache_read`，二者相加还原 input，缓存部分只计一次；
- `tier("base", expr)` 本波为**单层语义**：取第二个参数表达式的值（base 档唯一）；多层阶梯定价（按用量/上下文分档）在管理面配置就绪后扩展，表达式格式向后兼容；
- **表达式即终价，不叠乘 group_ratio**（组倍率已在表达式系数中表达或按需自乘）；
- 适用有阶梯价、缓存价的模型。

### 3. per_call（按次模式）

落地公式：

```
quota = round(per_call_price × group_ratio × 500000)
```

- 固定价格/次（美元），不依赖 tokens 计数；叠乘 group_ratio；
- 适合固定定价的模型与工具类端点。

### 4. 组倍率（GroupRatio）

- options `GroupRatio`：组名 → 值 JSON；本波所有请求归属 `default` 组（令牌分组在 M3 落地）；
- 回退语义：请求组未配置 → 取 `default` 组值 → 仍缺省取 1.0。

### 5. 价格查找顺序（落地）

三模式按模型粒度配置。落地查找顺序（DB 配置优先于内置价）：

1. options `billing_setting.billing_mode` 显式声明（tiered_expr 配 `billing_setting.billing_expr`、per_call 配 `billing_setting.billing_price`、classic_ratio 配 `ModelRatio`）；
2. options `ModelRatio` 命中该模型（隐式 classic_ratio，CompletionRatio 可缺省）；
3. 内置价单 `internal/billing/prices.json`（go:embed，启动校验 schema）；
4. 均未命中 → `ErrUnpriced`，显式拒绝服务。

**配置声明不完整（如声明 tiered_expr 但无表达式）视为未配价**：拒绝服务优于错扣。LookupPrice 返回不可变 ModelPrice 快照，单请求生命周期复用（防预扣与结算之间热更导致口径漂移）。

## 三、预扣费 + 多退少补

1. 请求进入时预扣估算：`Estimate = round(Charge({Input: len(body)/4, Completion: max_tokens（缺省 1024）}) × 1.2)`，最低 1 quota，先冻结（扣减 tokens.remain_quota）；
2. 冻结为**事务内条件 UPDATE**：`UPDATE tokens SET remain_quota = remain_quota - ? WHERE id = ? AND remain_quota >= ?`，RowsAffected=0 → `ErrInsufficientQuota`，映射 HTTP 403 `insufficient_quota` 拒绝请求（无副作用）；
3. 响应完成后按实际 usage 结算：差额 = 冻结 − 实结；实际 < 预扣 → 退还差额；实际 > 预扣 → 补扣差额（**允许透支到负数**，负数余额因条件 UPDATE 天然拒绝后续请求）；users.quota 与 tokens.remain_quota 同步扣减；
4. unlimited 令牌跳过账本三级操作（冻结/结算/退款），日志仍记实结 quota 并标记；
5. 结算明细写入 logs.detail（frozen/actual），预扣额与实结额都可追溯（对账依据）。

## 四、流中断退款与部分结算（M2-wave3 修订）

- **三分支口径「已发生即已消耗」**（`aborted` 终态下的结算选择）：
  1. **usage 已知**（如 anthropic `message_start` 先携带输入用量）→ 按已知 usage 部分结算，标记 `aborted` + `partial`（非粗估）；
  2. **usage 缺失但已写出内容**（`c.Writer.Size() > 0`）→ 按字节粗估部分结算：输入按请求体 /4、输出按已写字节 /4（`billing.BytesPerTokenEstimate`），标记 `aborted` + `partial` + `estimated`（粗估口径偏保守：缓存折扣不可知，按全价输入计）；
  3. **无任何消耗证据**（零写入）→ **全额退款**（退还全部预扣），标记 `aborted` + `refund_full`，实结 0；
- 设计取向不变：宁可少收不多收——结算计费环节失败（charge 出错）也按全额退款处理；
- usage 证据优先于字节粗估：同一中断两种证据并存时按 usage 结算；
- 落地修订：M1-wave3 曾「中断即全额退款」，M2-wave3 按本节三分支实现（设计稿「已知部分 usage 按部分结算」清偿），Detail 新增 `partial` 字段。

## 五、未配价硬拒绝

- 请求的模型无任何价格配置 → **直接拒绝**，绝不按 0 价放行；
- 落地映射 HTTP **503 `model_not_priced`**（设计稿写 4xx，落地修正为 503：价格缺失是服务端配置问题而非客户端过错，客户端无法通过修改请求修正；错误信息不含内部细节）；
- 令牌余额不足是客户端过错，映射 403 `insufficient_quota`（与未配价区分归因）；
- 「先上线后补价」通过 options 热更完成，配置即时生效；
- 该行为有黄金测试用例固化（TestGatewayUnpricedModel503），防止回归。

## 六、黄金测试集

- 概念：一组「输入（模式配置 + tokens 计数）→ 期望 quota」的固定用例，随代码版本维护；
- 落地路径：`internal/billing/testdata/golden/billing_cases.json` + `TestGoldenBilling`（逐位断言）；
- 来源：四条生产环境实测账单的数值转录（字段名中性化，文件内不含任何竞品名，并有竞品词自检测试）；
- 覆盖：tiered_expr 公式与四舍五入边界（round-up / round-down）、缓存拆分、tier() 语义、未配价拒绝（gateway 挂接侧）；
- 任何计费相关改动必须全量跑通黄金测试集，CI 阻断失败。

## 七、公式实测（M1-wave3 黄金样例）

四条实测账单数值与 tiered_expr 公式逐位对齐（`quota = round((p×单价 + c×单价 + cr×单价) × 500000 / 1e6)`，变量为原始 tokens 数，单价为 $/M）：

| 用例 | 表达式 | 输入 tokens | 输出 tokens | 缓存读 | 计算过程（micro-USD） | 期望 quota |
| --- | --- | --- | --- | --- | --- | --- |
| case-01-heavy-context | `p*0.15 + c*0.5 + cr*0` | 371253 | 3248 | 0 | (371253×0.15 + 3248×0.5) = 57311.95 → ÷2 = 28655.975 | **28656** |
| case-02-light-round-down | 同上 | 15 | 92 | 0 | (15×0.15 + 92×0.5) = 48.25 → ÷2 = 24.125 | **24** |
| case-03-repriced-round-up | `p*0.18 + c*0.6 + cr*0` | 15 | 114 | 0 | (15×0.18 + 114×0.6) = 71.1 → ÷2 = 35.55 | **36** |
| case-04-repriced-acceptance | 同上 | 15 | 60 | 0 | (15×0.18 + 60×0.6) = 38.7 → ÷2 = 19.35 | **19** |

- case-02/04 验证 round-down、case-03 验证 round-up（Go `math.Round` 半数远离零）；
- case-01 验证大用量精度（浮点累加后仍逐位命中）；
- 四条样例实测账单与本地公式零偏差，口径锚定可复算。

## 八、兑换码与令牌预算窗口（M2-wave3 落地）

### 1. 兑换码核销状态机

- 状态枚举：1=未使用、2=已核销、3=已作废、**4=已过期**（核销路径惰性标记）；
- 核销（`POST /api/user/topup`）：事务内「条件 UPDATE status 未用→已用（+ used_by/used_time）
  → 面额入账 users.quota → 写 topup 日志」三步原子完成，任何一步失败整体回滚（无部分入账）；
  并发重复兑换由条件谓词否决（RowsAffected=0 → 409 `redemption_used`）；
- 过期语义：`expired_time`（-1 永久）已过且状态未用时，**惰性标记 status=4 并随本事务提交**
  （拒绝响应在事务外映射 400 `redemption_expired`）——标记不因拒绝而回滚，状态收敛一次生效；
- 兑换后额度入**用户余额**，由用户自行划转到令牌（`POST /api/token/:id/assign`：条件扣减
  用户余额 `quota >= delta` 防透支 → 令牌 remain_quota 与 quota 同步增加 → 写 token_assign
  日志，同事务转移）；划转不是入账的必经步骤，用户余额也可仅沉淀；
- 对账：核销与划转各写一条 `protocol="topup"` 日志（ModelName 区分 redemption/token_assign，
  detail 含 event/ref_id/quota，不含兑换码明文）。

### 2. 令牌预算窗口（budget_duration）

- 取值：`''`（无周期，一次额度用完为止）/ `24h` / `7d` / `30d`（固定时长）/ `monthly`（自然月，
  相位对齐，目标月缺同号日钳制月末如 1/31→2/28）；`budget_reset_at`（unix 秒，0=未初始化）；
- **惰性重置**：转发鉴权路径检查（rollBudget）——首次请求 CAS 初始化窗口边界（只定界不重置）；
  已过期则从旧边界逐窗口步进至 now 之后（保相位），CAS `WHERE budget_reset_at=旧值` 复原
  remain_quota=quota 并写一条 budget_reset 日志；并发请求恰一次重置，其余按旧快照放行；
- 与余额关系：**窗口内消耗受 remain_quota 封顶**（与预扣费账本共用一列）——重置即「remain
  复原为 quota」，非清零重计；划转/管理面编辑须保持 `remain_quota <= quota` 不变式；
- 无请求不回补：窗口过期期间令牌闲置不产生任何写放大，语义为「下次请求时对齐」。
