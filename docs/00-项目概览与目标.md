# 00-项目概览与目标

> 状态：有效 | 负责人：hui-api 作者 | 本文回答「为什么做、做成什么样」。

## 一、项目定位

hui-api：为个人开发者与小团队打造的轻量 LLM API 网关——单二进制 + SQLite 零依赖、可靠多渠道路由与熔断、令牌预算与兑换码体系。

面向的场景：

- 个人开发者把散落的上游 API Key 统一收口，按项目/用途分发令牌；
- 小团队内部共享上游额度，令牌级预算与限流防止失控；
- 个人商业化场景：兑换码售卖额度，账目可查可对。

## 二、动机（中性表述）

市面上的自托管 LLM 网关产品普遍存在以下工程短板，hui-api 针对这些痛点而设计：

1. **配置热加载**：多数实现改配置需重启进程，生产环境切换渠道/调价有中断窗口；
2. **数据迁移工具**：缺少官方的、跨版本的数据导出导入路径，用户被锁死在单一部署形态；
3. **计费可对账**：预扣费与最终扣费口径不透明，流式请求中断后的退款语义含糊，账实难对；
4. **令牌安全默认值**：令牌明文落库或弱哈希、默认限流缺失、无标签分组等管理能力。

hui-api 把上述四点作为第一优先级工程目标，而非事后补丁。

## 三、总路线（M0-M5 波次概述）

| 里程碑 | 波次 | 目标概述 |
| --- | --- | --- |
| M0 | - | 建仓与环境准备：工程骨架、文档体系、CI、最小可运行入口 |
| M1 | wave1 | 存储层：六表模型、迁移框架、配置双轨热更 |
| M1 | wave2 | relay 转发链路：双协议端到端、渠道路由与熔断 |
| M2 | - | 计费内核：三模式计费、预扣费与多退少补、黄金测试集 |
| M3 | - | 令牌预算、兑换码、用户体系与管理 API |
| M4 | - | React 管理台 + 部署切换预案演练（旁路验证 → 端口接管） |
| M5 | - | 生产收尾：备份运维常态化、可观测完善、文档定稿 |

> 波次内任务拆解以 `10-里程碑与进度.md` 的「当前状态」块为准，本文只保留概述粒度。

## 四、非目标

- 不做上游模型训练、微调相关能力；
- 不做分布式多节点部署（单机单二进制是明确边界）;
- 不追求兼容所有上游协议，首发只覆盖 OpenAI 兼容与 Anthropic Messages 两种。
